# ESP32-C5 Wi-Fi CSI 非接觸式呼吸感測

用一片 ESP32-C5 開發板，從 Wi-Fi 訊號中偵測人的呼吸——不需穿戴任何裝置、不需攝影機。

> **C5 移植版**：本專案由 [ESP32-CSI](https://github.com/YANLUN-SU29/ESP32-CSI)（ESP32 + MERCUSYS N300）
> 移植到 **ESP32-C5 + TP-Link AC750 雙頻路由器**。韌體與 `monitor.py` 已改為 C5 的 CSI 格式，
> 分析工具（`analyzer_gui.py`、`batch_analyze.py`、`segment_analyze.py`）不需改動即可讀新格式。
>
> ⚠️ **第 8、9、11、13 節的門檻、成果與實驗數據全部來自前一版硬體。** C5 的子載波數
> （55 條 vs 110 條）、頻段（預設 5 GHz）、取樣率都不同，門檻**必須用 C5 的資料重新校準**
> 才能使用（流程見[第 8 節「重新校準流程」](#重新校準流程)）。與前一版的差異整理在
> [第 4 節](#4-硬體與環境)。

## 1. 這個專案在做什麼

從 ESP32 擷取 Wi-Fi 的底層通道資訊 (CSI, Channel State Information)，經訊號處理後判斷
**畫面外的人有沒有在呼吸、呼吸率是多少**。

適用情境：睡眠監測、長照看護——這類場合裝攝影機有隱私問題，戴感測器又不舒服。

**目前狀態**：呼吸偵測已完成兩日 40 筆驗證。通過門檻的檔案呼吸率推估誤差 ≤ 0.4 次/分（對節拍器 12.5 次/分，n=17，100% 命中）；二元有無判定的留一交叉驗證正確率 80.0%、跨日驗證 75~90%。
心跳與大動作偵測尚未校準。AI 建模尚未開始。

## 2. 原理：為什麼 Wi-Fi 能偵測呼吸

**CSI 是什麼**
Wi-Fi 用 OFDM 把一個通道切成很多條「子載波」，每條子載波各自有自己的通道響應。
CSI 就是這些響應的量測值，是**複數**——包含振幅（訊號衰減多少）與相位（延遲多少）。

**為什麼呼吸會影響它**
無線訊號從路由器到 ESP32 會經過多條路徑（直線、牆壁反射、人體反射），這些路徑疊加後
形成「多徑效應」。人的胸腔起伏會改變反射路徑的長度，進而改變疊加結果——所以 CSI 會隨
呼吸產生**週期性的微小變化**，頻率就是呼吸頻率（約 0.2 Hz，也就是 12 次/分）。

**為什麼這件事很難**
胸腔起伏造成的調變大約只有振幅的 **1%**，而 CSI 本身的變異主要來自：
- 寬頻雜訊
- AGC（自動增益控制）漂移
- 環境中其他物體的擾動

所以「把訊號濾到呼吸頻段然後看波形」是**行不通的**——帶通濾波後的波形永遠長得像正弦波，
**連空房間的資料也是**。這是本專案最重要的一個教訓，詳見
[第 8 節](#8-判定方法與校準)與[第 11 節](#11-開發過程中的重要發現)。

## 3. 系統架構與資料流

```
┌──────────────┐   Wi-Fi 封包    ┌──────────────┐
│  路由器 (Tx) │ ◄────────────── │  ESP32 (Rx)  │
│  TP-Link     │ ──────────────► │  ESP32-C5    │
│  AC750       │   回傳單播封包   │              │
└──────────────┘                 └──────┬───────┘
                                        │ USB 序列埠
                    ESP32 每收到一個封包就       │ 921600 baud
                    產生一次 CSI 事件            │ CSI_V4 文字行
                                        ▼
                              ┌────────────────────┐
                              │    monitor.py      │  即時錄製
                              │  ・解 I/Q → 振幅/相位 │
                              │  ・擷取 55 條子載波    │
                              │  ・即時視覺化 + 存 CSV │
                              └─────────┬──────────┘
                                        │ data/*.csv
                          ┌─────────────┴─────────────┐
                          ▼                           ▼
              ┌────────────────────┐    ┌────────────────────┐
              │  analyzer_gui.py   │    │  batch_analyze.py  │
              │  單檔互動式分析      │    │  整批分析 + 門檻校準  │
              └────────────────────┘    └────────────────────┘
```

**關鍵設計:ESP32 為什麼要主動戳路由器**

ESP32 的 CSI 引擎只在收到**單播**封包時才會觸發，廣播封包（如信標）會被過濾掉。
所以韌體必須主動製造往返流量：每 10ms 向路由器 Port 80 送一個極小的 TCP 封包，
逼路由器回傳 ACK，才能持續產生 CSI 事件。這就是程式碼裡說的「TCP 敲門」。

**分析流程（`analyzer_gui.py` / `batch_analyze.py` / `segment_analyze.py` 共用）**

```
55 條子載波振幅（前一版為 110 條）
   │
   ├─ 逐條清理：Rolling MAD 去離群值 → 線性去趨勢
   │
   ├─ 逐條帶通濾波到目標頻段（呼吸 = 0.15~0.4 Hz）
   │      ⚠️ 順序關鍵：必須「先濾波再融合」，不可顛倒（見第 11 節）
   │
   ├─ PCA 融合成 PC1 波形 ──────────────► 給人看的波形圖
   │
   └─ 逐條算 Welch PSD ────────────────► 判定用的客觀指標
            ├─ 峰值突出度
            └─ 載波共識度
```

## 4. 硬體與環境

| 角色 | 設備 | 設定 |
|------|------|------|
| **發射端 (Tx)** | TP-Link AC750 雙頻路由器（Wi-Fi 5） | 建議 5 GHz、**頻寬固定 20MHz**、固定通道 |
| **接收端 (Rx)** | ESP32-C5 開發板（如 ESP32-C5-DevKitC-1） | 接 **UART 埠**（USB 轉序列晶片那個） |
| **監測端** | Windows PC | Python 3.12 |

**Python 相依套件**（`requirements.txt`）：`numpy`、`scipy`、`pandas`、`scikit-learn`、
`matplotlib`、`pyserial`

**Arduino 環境**：ESP32 board package **3.3.0 以上**（C5 需要 ESP-IDF 5.5；已用 3.3.10 編譯通過）。
韌體用到 ESP-IDF 內建的 `esp_ping`，不需額外安裝函式庫。

**路由器設定建議**（TP-Link 管理頁面 → 無線設定）：
- 2.4 GHz 與 5 GHz **用不同的 SSID**，或在韌體 `WIFI_USE_5G` 指定頻段，避免重連時跳頻段
- 5 GHz **頻寬設 20MHz**、**通道固定**（不要自動）。韌體已在 STA 端宣告只支援 20MHz，
  但路由器端也鎖住最保險；若結束報告出現「次通道」警告就是這裡沒設好
- 管理頁面維持在 Port 80（TCP 敲門的目標）

**與前一版（ESP32 + N300）的差異**

| 項目 | 前一版 | C5 版 | 影響 |
|------|-------|-------|------|
| 頻段 | 2.4 GHz（ch6） | 預設 5 GHz（可切回 2.4） | 波長 12.5 → 5.7 cm，同樣位移相位變化約 2.2 倍 |
| 每封包 LTF | LLTF + HT-LTF 串在一起 | 只有一種（HT-LTF 或 VHT-LTF） | 子載波 110 → 55 條 |
| CSI 長度 | 256 bytes | 114 bytes | 序列埠每行約縮短一半 |
| CSI 設定 | `lltf_en`、`htltf_en`… | `acquire_csi_ht20`、`acquire_csi_vht`… | API 不相容，韌體不能共用 |
| 封包型別欄位 | `rx_ctrl.sig_mode` | `rx_ctrl.cur_bb_format` | 輸出格式 V3 → V4 |
| 來源過濾 | 無 | 只收路由器 BSSID | 鄰居流量不再混入 |
| 硬體自報無效 | 無 | `rx_channel_estimate_info_vld`、`first_word_invalid` | 無效幀丟棄並計數 |

## 5. 快速開始

### 步驟 1：燒錄韌體

1. Arduino IDE 開啟 `firmware.ino`（Arduino IDE 要求 `.ino` 放在同名資料夾，
   即 `firmware/firmware.ino`，IDE 會提示自動建立）
2. 修改 `ssid` 與 `password` 為你的路由器設定；`WIFI_USE_5G` 選頻段（1 = 5 GHz，0 = 2.4 GHz）
3. 開發板選 **ESP32C5 Dev Module**，燒錄
4. **燒完務必關掉 Arduino IDE 的序列埠監控視窗**——序列埠一次只能被一個程式開啟

> 若用開發板上的 USB（原生 USB-Serial/JTAG）埠而非 UART 埠，需把 Tools → USB CDC On Boot
> 設為 Enabled，否則看不到輸出。UART 埠不需改設定，建議用它。

### 步驟 2：安裝 Python 套件

```bash
pip install -r requirements.txt
```

### 步驟 3：錄製資料

```bash
python monitor.py EMPTY01
```

會開啟一個即時視覺化視窗並同時寫入 `data/CSI_EMPTY01_<時間>.csv`。
關閉視窗即結束錄製。

啟動時應該看到：

```
[自動] 鎖定唯一 USB 裝置：COM3 (Silicon Labs CP210x USB to UART Bridge)
[連線] 已開啟 COM3 @ 921600 baud
[韌體] CSI_V4 格式 | 原始長度 114 bytes (57 條子載波) | RSSI -45 dBm | VHT | 通道 36 (5GHz)
[擷取] HT/VHT-LTF 55 條（子載波 -28~-1、+2~+28，已剔除 DC 與 first_word 無效的 +1）
[記錄] 振幅 + 相位，CSV 共 111 欄
```

（上面的 RSSI、型別與通道依實際環境而定；2.4 GHz 時型別為 HT。長度**必須是 114**，
否則代表路由器送的不是 20MHz 封包，結束報告的「佈局不符丟棄」會很大。）

結束時會輸出品質報告，**這兩個數字要是 0**：

```
- 訊號斷點：0 次
【丟失率分析】總丟失率：0 筆 (0.00%)   ✓ 無任何丟失
```

不是 0 的話那筆資料品質有疑慮，建議重錄。

### 步驟 4：分析

```bash
# 單檔互動式檢視
python analyzer_gui.py

# 整批分析 + 門檻校準
python batch_analyze.py
```

## 6. 程式詳解

### `firmware.ino` — ESP32 韌體

| 設定 | 預設值 | 說明 |
|------|-------|------|
| `WIFI_USE_5G` | `1` | 頻段。1 = 只連 5 GHz；0 = 只連 2.4 GHz（固定頻段，避免重連跳頻段） |
| `USE_ICMP_PING` | `0` | 觸發方式。0 = TCP 敲門（前一版已驗證）；1 = ICMP ping（程式碼備用，未實測） |
| `CSI_QUEUE_LEN` | `24` | CSI 事件佇列長度（約 12.6KB） |
| `csi_config` | HT20 + VHT 開、其餘關 | 只收 20MHz 的 HT/VHT 封包，佈局固定為 114 bytes |
| 頻寬 | HT20 | `esp_wifi_set_bandwidths` 在 STA 端宣告只支援 20MHz |

**架構重點**：CSI 回呼**只**把資料丟進 FreeRTOS 佇列就返回，絕不在回呼裡做序列埠輸出。
原因見[第 11 節](#11-開發過程中的重要發現)。輸出由 `loop()` 負責排空。
回呼另外會過濾掉非路由器 BSSID 的封包，以及硬體標記通道估計無效的幀。

**輸出格式**：
```
CSI_V4,<序號>,<長度>,<RSSI>,<型別>,<累計丟棄>,<主通道>,<次通道>,<fwi>,<虛1>,<實1>,<虛2>,<實2>,...
```
- `型別` = `rx_ctrl.cur_bb_format`（1=11a/g、2=HT、3=VHT、4~7=HE）
- `次通道` = 0 表示 20MHz；1/2 表示 40MHz 的上/下次通道
- `fwi` = `first_word_invalid`，1 表示前 4 bytes（前兩條子載波）因 C5 硬體限制無效
- 每條子載波兩個 int8，**虛部在前、實部在後**（ESP-IDF 文件）

### `monitor.py` — 即時錄製

| 設定 | 預設值 | 說明 |
|------|-------|------|
| `RECORD_PHASE` | `True` | 是否一併記錄相位（CSV 由 56 欄變 111 欄） |
| `GAP_WARN_THRESHOLD` | `0.5` | 超過幾秒沒收到資料就警告 |
| `WINDOW_SIZE` | `100` | 即時視覺化的滑動視窗幀數 |
| `SUBCARRIER_IDX` | — | 子載波擷取索引，依實測佈局寫定（見[第 7 節](#7-csv-資料格式)） |

**用法**：
```bash
python monitor.py            # 互動模式，程式會問標籤
python monitor.py EMPTY01    # 直接指定標籤
```

> ⚠️ 程式內的 `VALID_LABELS = ["Empty_Room", "Walking", "Waving"]` 是早期遺留的預設選項，
> 與現行資料集命名（`EMPTY01`、`GEO_P0`、`HOLD_P10`）不符。直接用命令列指定標籤即可。

### `analyzer_gui.py` — 單檔互動分析

四種分析模式，用 RadioButton 切換：

| 模式 | 頻段 | 用途 | 已校準 |
|------|------|------|--------|
| 大動作 | 0.05 ~ 5.0 Hz | 走動、起立坐下 | ✗ |
| **呼吸** | **0.15 ~ 0.4 Hz** | **靜止人員呼吸** | **✓** |
| 心跳 | 0.8 ~ 2.0 Hz | 心跳偵測嘗試 | ✗ |
| 空房間基準 | 0.05 ~ 5.0 Hz | 確認無人時底噪 | ✗ |

> 突出度的數值尺度會隨頻段寬度系統性改變，所以門檻只在有 ground truth 的頻段成立。
> 未校準的頻段 GUI 會顯示灰色「尚無實測校準」，數值僅供不同檔案間相互比較。

**三層圖表**：
1. **全景子載波疊加** — 觀察多徑衰落，並標出該頻段最強的一條
2. **目標頻段融合波形** — 先帶通、再 PCA 融合的結果
3. **功率頻譜 (Welch PSD)** — 縱軸正規化為突出度倍率，可直接對照門檻線

> ⚠️ **判讀請以第 3 張圖為準。** 第 2 張的波形無論有沒有人都像正弦波，
> 空房間資料同樣會呈現規律起伏——這正是需要客觀指標的原因。

### `batch_analyze.py` — 批次分析與校準

```bash
python batch_analyze.py                # 分析振幅（預設）
python batch_analyze.py --phase        # 一併分析相位
python batch_analyze.py --band heart   # 改分析心跳頻段
python batch_analyze.py --no-cache     # 忽略快取重算
```

輸出內容：逐檔指標 → 分組彙總 → 各指標 AUC → 現行門檻驗證 →
**留一交叉驗證（誠實估計）** → 零誤報門檻掃描。

分組規則依檔名前綴：`CSI_EMPTY*` → 對照組、`CSI_GEO_<位置>*` → 呼吸、
`CSI_HOLD_<位置>*` → 閉氣。

> ⚠️ 本程式是**整檔**分析。`CSI_HOLD_*` 整檔並不是「沒有呼吸」的樣本
> （只有中間 30 秒是），因此它已從負樣本中排除——要用憋氣段當負樣本請改用
> `segment_analyze.py`。

### `segment_analyze.py` — 分段分析（以憋氣段為負樣本）

```bash
python segment_analyze.py                  # 每段 24 秒（預設）
python segment_analyze.py --seconds 20     # 改變片段長度
python segment_analyze.py --save seg.csv   # 另存逐片段指標（畫圖或寫報告用）
```

把**所有**檔案切成等長片段後才比較，因為突出度的尺度會隨 Welch 平均段數改變，
30 秒的憋氣段不能直接和 120 秒的整檔相比。分段對齊 `HOLD` 的錄製協定
（呼吸前段 3~27s、憋氣段 33~57s、呼吸後段 63~87s，避開舉手前後 3 秒）。

輸出內容：各狀態（呼吸／憋氣／空房間）彙總 → 片段層級 AUC →
**HOLD 檔內配對比較 + 符號檢定**。

最後那項是全案最嚴格的對照：同一個人、同一位置、同一天、相隔數十秒，
唯一的差異就是有沒有在呼吸。

## 7. CSV 資料格式

C5 版格式共 **111 欄**：

| 欄位 | 說明 |
|------|------|
| `Timestamp` | 錄製時間戳（`HH:MM:SS.ffffff`，微秒精度） |
| `H-28_A`~`H-1_A`、`H2_A`~`H28_A` | 55 條子載波的**振幅** |
| `H-28_P`~`H-1_P`、`H2_P`~`H28_P` | 對應的**原始相位**（弧度，未做 CFO/SFO 校正） |

欄名規則：`H` = HT/VHT-LTF，數字是**實體子載波編號**（-28 ~ +28，依頻率由低到高排列），
`_A` = 振幅、`_P` = 相位。（注意與前一版不同：前一版的數字是原始陣列索引。）

**C5 的子載波是怎麼挑的**

韌體輸出 114 bytes = 57 條子載波。依 ESP-IDF 文件，C5 HT20/VHT20 的陣列順序為
「索引 0~28 → 子載波 0~+28，索引 29~56 → 子載波 -28~-1」。

| 子載波 | 陣列索引 | 處理 |
|-------|---------|------|
| 0 | 0 | 剔除：DC，文件列為無效子載波 |
| +1 | 1 | 剔除：C5 的 `first_word_invalid` 會讓前 4 bytes 無效，為保持欄位一致一律剔除 |
| +2 ~ +28 | 2 ~ 28 | 取用（27 條） |
| -28 ~ -1 | 29 ~ 56 | 取用（28 條） |

長度不是 114 的幀（STBC 228、HT40 234…）整幀丟棄並計入「佈局不符丟棄」。

> 此佈局依官方文件寫定，**尚未用 C5 實機資料驗證**。前一版就曾因佈局假設錯誤而少取
> 一半子載波（見第 11 節），第一次錄製後請用 `analyzer_gui.py` 確認沒有恆為零或明顯離群的欄位。

**前一版（ESP32）的子載波佈局**（僅供讀取舊資料參考）

韌體輸出 256 bytes = 128 條子載波，分成兩個 64 條的區塊。實測量出的佈局：

| 區塊 | 索引範圍 | DC 離群值 | 保護頻帶 | 取用 |
|------|---------|----------|---------|------|
| LLTF | 0 ~ 63 | idx 0（振幅 134.4，區塊中位數僅 17.6） | 28 ~ 36 | `1~27` + `37~63`（54 條） |
| HT-LTF | 64 ~ 127 | idx 64 | 93 ~ 99 | `65~92` + `100~127`（56 條） |

`analyzer_gui.py` 會依 `_A` / `_P` 後綴**只取振幅欄**做分析——相位的物理意義與尺度都
與振幅不同，混進同一個 PCA 會破壞融合結果。

**向下相容**：三種歷史格式都能讀（已回歸測試）

| 格式 | 總欄數 | 分析取用 | 有效載波 |
|------|-------|---------|---------|
| 最舊 `Sub_0`~`Sub_51` | 53 | 52 欄 | 43（動態剔除 9 條全零） |
| 中間版 `L1`~`H127`（無後綴） | 111 | 110 欄 | 110 |
| 前一版含相位 `_A`/`_P` | 221 | 僅 110 個 `_A` 欄 | 110 |
| C5 版 `H-28_A`~`H28_P` | 111 | 僅 55 個 `_A` 欄 | 55 |

## 8. 判定方法與校準

### 為什麼不能看波形

帶通濾波後的波形永遠像正弦波，**空房間也一樣**。這是濾波器的必然結果，不是訊號。
早期曾以「Welch PSD 在 0.15~0.4 Hz 抓到峰值」作為偵測成功的依據，但後來加入對照組
才發現**空房間同樣會在該頻段長出峰值**，那個結論是空的。

### 兩個客觀指標

| 指標 | 定義 | 意義 |
|------|------|------|
| **峰值突出度** | 最強子載波的帶內峰值 ÷ 帶內雜訊中位數 | 訊號比雜訊突出幾倍 |
| **載波共識度** | 前 10 強子載波中，峰值頻率彼此一致的比例 | 多條子載波是否**獨立地**收斂到同一頻率 |

**判定只用突出度，共識度只做輔助顯示。** 這一點在 2026-09-10 第二批資料進來後改過：
原本把共識度當成必要的 AND 條件，跨日驗證證實那樣反而更差（詳見
[§9 判定規則：為什麼拿掉共識度](#判定規則為什麼拿掉共識度)）。
共識度會隨當日訊號強弱整體浮動，門檻搬不過去；突出度則相對穩定。

### 現行門檻

```
突出度 ≥ 6.5   →   高信心（判定為偵測到呼吸）
突出度 ≥ 3.5   →   中等信心（有跡象但不明確）
其餘            →   低信心

共識度 < 70% 時，畫面上會在判定後面加註「僅 N% 子載波認同此頻率，建議重錄確認」
```

在 40 筆（24 呼吸 / 16 對照）上：命中 17/24、誤報 0/16。

> ⚠️ **突出度的數值尺度會隨 `WELCH_WINDOW_SEC` 改變。**
> 若調整 Welch 窗長，門檻必須連同重新校準。兩者定義在 `analyzer_gui.py` 開頭，
> 並在註解中互相標註。

**Welch 窗長為什麼是 30 秒**

窗越短→分段越多→平均越充分→假峰值越少，代價是頻率解析度變差。實測掃描：

| 窗長 | 頻率解析度 | AUC | 對照組最高分 |
|------|-----------|-----|------------|
| 60s | 0.017 Hz | 0.917 | **24.0**（約 1~2 段平均，幾乎沒平均到） |
| **30s** | **0.033 Hz** | **0.958** | **5.5**（約 4 段平均） |
| 20s | 0.050 Hz | 0.958 | 3.1（解析度不足，命中率反而掉） |

（此表為 2026-09-08 那 20 筆上的掃描結果，尚未用 40 筆重跑；窗長維持 30s。）

實測對照組的「錄製時長 vs 突出度」相關係數為 **r = −0.818**——錄越短、假峰值越高，
證實假峰值來自 Welch 平均不足。

### 重新校準流程

錄了新資料之後：

```bash
python batch_analyze.py
```

看輸出的「零誤報門檻掃描」與「留一交叉驗證」，決定新門檻後改
`analyzer_gui.py` 的 `TH_HIGH_PROM`。

> 資料跨越多天時，別只看留一交叉驗證——**務必另外做跨日驗證**
> （用一天選門檻、套到另一天）。留一會把同一天的鄰近樣本混進訓練集，
> 仍然偏樂觀；本專案就是靠跨日驗證才發現共識度條件是有害的。

基於 **40 筆** 資料：2026-09-08 錄 20 筆、2026-09-10 再錄 20 筆，
每日皆為空房間 5、呼吸 12（P0/P05/P10/P15 各 3）、閉氣 3。110 條含相位格式。

### 分組結果（兩日合併）

| 組別 | n | 突出度（平均） | 共識度 | 推估呼吸率 |
|------|---|--------------|-------|-----------|
| EMPTY（無人） | 10 | 3.2 | 59% | 18.1 ± 3.5 次/分 |
| HOLD（見下方警告） | 6 | 4.2 | 87% | 12.6 ± 5.1 次/分 |
| GEO_P0 | 6 | 12.9 | 93% | 12.3 ± 0.2 次/分 |
| GEO_P05 | 6 | 11.2 | 87% | 12.8 ± 0.5 次/分 |
| GEO_P10 | 6 | 10.3 | 88% | 11.8 ± 0.8 次/分 |
| GEO_P15 | 6 | 13.1 | 100% | 12.3 ± 0.2 次/分 |

> ⚠️ **HOLD 那一列是整檔統計，不具「沒有呼吸」的意義**——該檔 2/3 的時間受測者
> 確實在呼吸。詳見下方「HOLD 不是整檔的負樣本」。

呼吸組的推估頻率集中在 11.8~12.8 次/分、組內標準差 ±0.2~0.8，跨兩日、跨四個位置
都落在同一個窄範圍；EMPTY 則隨機散佈（±3.5）。
**頻率推估是全案最穩的一項結果**，連突出度不到門檻的檔案也多半報出正確的呼吸率。

### 呼吸率推估準確度（有 ground truth）

錄製時以線上節拍器 **25 BPM、兩拍完成一次呼吸**引導，即目標 **12.5 次/分**。
以此為 ground truth 計算 24 筆呼吸資料的推估誤差：

| 分組 | n | MAE | 平均偏差 | RMSE | 最大誤差 | 落在 ±0.5 內 |
|------|---|-----|---------|------|---------|------------|
| **突出度 ≥ 6.5（通過門檻）** | **17** | **0.19 次/分** | −0.10 | 0.23 | **0.40** | **100%** |
| 突出度 < 6.5（未通過） | 7 | 0.87 | −0.40 | 1.11 | 1.87 | 43% |
| 全部 24 筆 | 24 | 0.39 | −0.19 | 0.63 | 1.87 | 83% |

分日看：09/08 的 MAE 0.28、平均偏差 **+0.08**；09/10 的 MAE 0.50、平均偏差 −0.45
（後者主要由兩筆弱訊號檔案 P10_R1/R3 拉低，推估 10.6 / 10.7）。

依位置：P15 MAE 0.19、P0 0.21、P05 0.40、P10 0.76。

**這是全案最強的一項結果。** 突出度通過門檻時，呼吸率誤差不超過 0.4 次/分
（相對誤差 3.2%），24 筆中 17 筆全部命中；而突出度不通過時誤差就散掉了。

換句話說，兩個指標分工明確：

- **突出度**回答「這筆資料可不可信」
- **峰值頻率**回答「呼吸率是多少」

而且 —— **6.5 這個門檻原本只是為了在對照組上達到零誤報而選出來的，
它同時也精確切開了「頻率準」與「頻率不準」**。兩個互相獨立的標準收斂到同一個門檻，
是這個門檻站得住腳的獨立證據。

對照組不會湊巧落在 12.5 附近：EMPTY 只有 10%、HOLD 只有 17% 落在 12.5±0.5 內
（EMPTY 平均 18.1 ± 3.5、HOLD 12.6 ± 5.1）。

> ⚠️ **目前 24 筆呼吸資料全部只有 12.5 次/分這一個速率。**
> 這證明了系統在該速率下很準，但還不足以證明它是在「量測」呼吸率而非恰好對上 0.2 Hz。
> 需要改變節拍器速率（例如 20 / 30 / 40 BPM → 10 / 15 / 20 次/分）重錄才能排除這個質疑。

### ⚠️ HOLD 不是整檔的負樣本（2026-09-16 修正）

`HOLD` 的錄製協定是 **0~30s 正常呼吸 → 舉手 → 30~60s 憋氣 → 舉手 → 60~90s 恢復呼吸**，
也就是**整檔有 2/3 的時間受測者確實在以 12.5 次/分呼吸**。

在 2026-09-16 以前，本專案把 HOLD 整檔當成「沒有呼吸」的負樣本，那是錯的。
所有把 HOLD 計入負樣本的判別力數字都要重算，下面的表已是修正後的版本。

真正的負樣本是中間那 30 秒憋氣，分析方式見 [`segment_analyze.py`](segment_analyze.py)。

### 判別力（負樣本只有 EMPTY）

| 指標 | 數值 |
|------|------|
| AUC（GEO vs EMPTY，兩日合併） | **0.958** |
| **留一交叉驗證正確率** | **82.4%**（敏感度 79.2%、特異度 90.0%） |
| 同批評估正確率 | 79.4%（命中 17/24、誤報 **0/10**，特異度 100%） |

### 呼吸 vs 憋氣：真正的對照

只用 EMPTY 當負樣本，只能證明「偵測得到有沒有人」，不能證明「偵測得到的是呼吸」。
憋氣段才是那個關鍵對照——有人在場、姿勢相同，唯一差異是有沒有呼吸。

**HOLD 檔內配對比較**（每段 24 秒，避開舉手前後 3 秒）：

|------|-----------|-------|------|
| HOLD_P10_R1_0908 | 36.4 | 11.7 | 3.12× |
| HOLD_P10_R1_0910 | 24.4 | 8.4 | 2.91× |
| HOLD_P10_R2_0908 | 24.0 | 22.3 | 1.08× |
| HOLD_P10_R2_0910 | 30.4 | 9.8 | 3.11× |
| HOLD_P10_R3_0908 | 46.2 | 11.2 | 4.10× |
| HOLD_P10_R3_0910 | 25.2 | 11.9 | 2.11× |

**6/6 的檔案呼吸段都高於憋氣段**（單尾符號檢定 p = 0.0156）。

### 憋氣段太短，不能用一般流程評估

憋氣只有 30 秒，而 Welch 窗長就是 30 秒——等於完全沒有分段平均，
正是先前已知會產生假峰值的情況。把所有檔案都切成 24 秒片段後實測：

| 狀態 | n | 突出度中位 | 四分位 |
|------|---|-----------|-------|
| 呼吸 | 83 | 18.0 | 13.0 ~ 28.6 |
| 憋氣 | 6 | 11.5 | 10.1 ~ 11.9 |
| 空房間 | 30 | 12.8 | 8.8 ~ 18.7 |

片段層級的判別力：呼吸 vs 空房間 AUC 只有 **0.684**（整檔 120 秒時是 0.958）。
**這反過來確認了「錄製長度必須夠」這件事**——24 秒的片段連空房間都分不出來，
所以憋氣段的絕對數值不能直接拿來當判定依據，只有**檔內配對比較**是可信的。

| 日期 | GEO 突出度中位 | EMPTY 突出度中位 | 該日 AUC |

### 判定規則：為什麼拿掉共識度

原本的規則是「突出度 ≥ 5.5 **且** 共識度 ≥ 90%」。兩日資料出來後，
以跨日方式重新比較各種規則（參數一律只在訓練日上選）：

| 規則（負樣本只有 EMPTY） | 09/08→09/10 | 09/10→09/08 | 平均 | 合併留一 |
|------|------------|------------|------|---------|
| **只看突出度** | 76.5% | 82.4% | 79.4% | **82.4%** |
| 突出度 + 共識度 | 70.6% | 88.2% | 79.4% | 76.5% |

**加上共識度沒有幫助。** 留一交叉驗證明顯偏向只看突出度（82.4% vs 76.5%），
跨日則是平手（79.4% vs 79.4%）。共識度會隨當日訊號強弱整體浮動，門檻搬不過去。

> ⚠️ **修正紀錄。** 這張表最初是把 HOLD 誤當負樣本算出來的，當時顯示
> 「只看突出度」在跨日上大勝（82.5% vs 77.5%）。排除 HOLD 後差距縮小為平手。
> **結論（採用較簡單的單一條件）不變，但證據強度比原先聲稱的弱。**
所以現在只用突出度單一條件，共識度改成畫面上的輔助資訊——低於 70% 時
會在判定後面加註「僅 N% 子載波認同此頻率，建議重錄確認」。

### 試過但沒用的：時間穩定度

觀察到呼吸組的推估頻率極度集中（11.8~12.8），對照組則散在 9~24，
於是設計了「時間穩定度」：把錄製切成 3 段，每段各自對前 10 強子載波
求帶內峰值頻率，共 30 個估計值，算有多少比例落在中位數 ±0.02 Hz 內。
想法是這個指標不受當日訊號強弱縮放影響，應該更耐跨日。

實測 AUC 僅 0.840，低於突出度的 0.924；加進判定規則也沒有幫助（見上表）。
**已否決**，但保留紀錄避免重做。同樣被否決的還有把突出度的分母
從「帶內中位數」換成「帶外 0.6~2 Hz 雜訊底」（AUC 0.763，更差）。

## 10. 常見問題與陷阱

### 找不到 COM Port / `OSError(22, '參數錯誤')`

ESP32 沒被 Windows 認到。`monitor.py` 只會挑有 VID/PID 的 USB 裝置，所以不會誤鎖主機板
內建的 COM1，但仍需檢查：

1. **USB 線** — 很多充電線只有供電、沒有資料線，這是最常見的原因
2. **驅動** — ESP32-C5-DevKitC-1 的 UART 埠多為 CP2102N 或 CH343，要裝對應驅動
3. **裝置管理員** — 看「連接埠」或「其他裝置」有無帶驚嘆號的項目
4. 換一個 USB 孔（前面板孔有時供電不足）

### 序列埠被佔用

`monitor.py`、`batch_analyze.py`（不需序列埠）、Arduino IDE 的序列埠監控視窗
**不能同時開著**。錄製前先確認只有一個程式在用。

### 錄完發現丟失率不是 0

看終端機的丟失率分析：
- **「韌體自報丟棄」> 0** → 序列埠排不及，可加大 `CSI_QUEUE_LEN`
- **「序號跳號」> 0** → 傳輸中遺失
- **「行截斷損壞」> 0** → 序列埠壅塞導致行被切斷

### 開機時出現一筆解析錯誤

正常。ESP32 重開機時會吐出一段二進位開機訊息，`monitor.py` 會把它記為 1 筆解析錯誤。
該筆**不會**被算進丟失率（那是刻意分開計數的）。

### 帶通後的波形看起來有呼吸，但判定是低信心

**相信判定，不要相信波形。** 帶通濾波器的輸出永遠像正弦波。請看第 3 張 PSD 圖，
確認峰值有沒有超過門檻線。

### 錄製時長建議

至少 **2 分鐘**。Welch 窗長是 30 秒，錄 100 秒約有 4 段平均，錄 120 秒有 7 段——
段數越多，對照組的假峰值越被壓下去。

## 11. 開發過程中的重要發現

這一節記錄「為什麼程式碼長這樣」。**修改前請先讀過對應項目**，這些都是踩過坑才得到的。

### PCA 融合的順序不能顛倒

常見做法是「PCA 融合 → 帶通濾波」。實測顯示這樣**完全分不出有人呼吸與空房間**
（呼吸組 3.48 vs 空房間 3.60，Cohen's d = −0.07）。

原因：PCA 以最大化變異量為目標，而原始振幅的變異由寬頻雜訊與 AGC 漂移主導，
遠大於胸腔起伏的約 1% 調變——PC1 鎖到的是**雜訊主軸**，不是生理訊號。

改成「逐條帶通 → 再 PCA 融合」後才明顯分離（65.90 vs 3.45）。

### 判定要用最強單一子載波，不是融合訊號

融合訊號適合畫波形給人看，但拿來判定的判別力差很多（AUC 0.74 vs 1.00）。
現行判定只走「最強單一子載波突出度」。

### 子載波擷取範圍曾經是錯的

舊版寫死 `amplitudes[5:57]`，結果：
- 存了 9 條**恆為零**的保護頻帶（52 欄裡有 17% 是垃圾）
- 視窗兩端切在**滿振幅**上（漏掉 LLTF 的 11 條有效子載波）

實測量出佈局後改為依區塊選取，可用子載波由 43 條增至 110 條（+156%）。
另發現 STBC-HT-LTF2 區塊與 HT-LTF 的逐條相關係數達 **0.902**（冗餘），予以捨棄；
而 HT-LTF 與 LLTF 相關性僅 **0.06**，是獨立的通道量測，值得納入
——初期 20 筆時單用 HT-LTF 的 AUC (0.948) 甚至高於單用 LLTF (0.917)；
擴充到 40 筆後兩者互換（LLTF 0.891、HT-LTF 0.844），但都低於「全部一起看」的 0.924，
所以維持兩區塊合併使用。

### fps 的瓶頸在序列埠，不在 MAC 層

曾依「每 78ms 週期有 47ms 閒置」推論 fps 卡在 59 是路由器 TCP delayed ACK 所致，
**此判斷有誤**。

證據：把每行長度縮到 2/3（384→256 bytes）後，樣本間隔中位數**精確地**由 8.00ms
降到 5.00ms、fps 升到 85。這個等比關係說明叢發內的間隔就是序列埠傳一行的時間
——序列埠排不及時，ESP32 端的 CSI 事件就被丟棄。

### CSI 回呼裡不能做序列埠輸出

回呼跑在 Wi-Fi driver task 的 context。一行約 490 bytes 在 921600 baud 下需約 5ms 的
阻塞寫入，會卡住該任務，使驅動**不再送入後續 CSI 事件**——而這種「事件根本沒進到回呼」
的損失，在 PC 端連計數器都測不到。

所以回呼只做 `memcpy` 進佇列（非阻塞），由 `loop()` 排空。佇列滿就明確計數，
損失才從不可見變成可量測的數字。

### PC 端時間戳受 USB 幀率量化

樣本間隔全都落在整數毫秒上（8.000 / 47.000 ms），這是 USB 1ms 幀率的特徵。
也就是說 PC 端量到的間隔反映的是 **USB 交付節奏**，不是 CSI 真正被擷取的時刻。
要解析真實取樣時序，需要在韌體端加入 `esp_timer_get_time()`（尚未實作）。

### 相位目前不可用

已錄下原始相位，但以 unwrap + 逐封包跨子載波線性去趨勢處理後，AUC 僅 **0.331**
（40 筆；初期 20 筆時為 0.375，都遠低於 0.5，即反向）。
所有組別（含空房間）的推估頻率都收斂到頻段下緣、
共識度多為 100%，全部擠在頻段下緣 0.15 Hz 附近——這是**殘留低頻漂移洩漏**的特徵，
不是呼吸訊號。

不代表相位本身沒價值（文獻上相位常比振幅靈敏），但現行校正方法顯然不足。
可嘗試的方向：更強的高通、或改用子載波間的相位差（conjugate multiplication）。

## 12. 已知限制

### 跨日不穩定（目前最大瓶頸）

09/08 那批的 AUC 是 0.958，09/10 這批掉到 0.885；用 09/08 選門檻套到 09/10，
正確率只有 75.0%。呼吸訊號的絕對強度在兩天之間差了約 3.5 倍，而對照組沒變
——問題出在**物理佈置的可重現性**，不在演算法。

要解決，必須先能重現佈置：把人與兩端設備的距離、朝向、高度、姿勢固定並記錄下來
（見 [§13 實驗配置](#13-實驗配置)）。只補資料量而不控制佈置，只會讓分佈更散。

配置已於 2026-09-16 補齊，並由此算出**頭號嫌疑**：在 `P15`，坐姿位置只要偏 1.92 cm
就會從 Fresnel 靈敏度極大跑到盲點。詳見 §13「幾何推算」。

### 資料量仍然不足

對照組 16 筆、呼吸 24 筆。特異度已從 75% 升到 93.8%，但敏感度只有 70.8%
——24 筆呼吸裡有 7 筆突出度不到門檻。

建議補到：至少再加一個**不同日**的完整批次（EMPTY 5、每位置呼吸 3、HOLD 3），
讓跨日驗證有三天可以互相檢驗，而不是只有兩天互推。

### `GEO_P05` 之前偏弱，補資料後未重現

09/08 那批 P05 平均只有 7.7（其他位置 15~20），一度懷疑是位置本身的幾何問題。
09/10 補了 3 筆後，P05 兩日合併平均 11.2，與 P10 的 10.3 相當，
反而是**同一位置的日間差異**大於位置之間的差異。原先的懷疑不成立。

### 僅呼吸頻段完成校準

心跳（0.8~2.0 Hz）與大動作（0.05~5.0 Hz）頻段缺乏對照組資料，GUI 已標示為未校準。

> 曾在住家測試中於心跳頻段看到突出度 90.8、推估 69.1 次/分（落在合理靜息心率範圍），
> 但該頻段零校準，且環境漂移的能量會漏進 0.8~2.0 Hz，**不可視為偵測到心跳**。

### C5 版尚未實機驗證

C5 韌體已編譯通過，但子載波佈局、fps、丟失率都還沒有實測數據。前一版的 fps（85）與
丟失率結論不能直接套用。第一次錄製請特別確認結束報告中的：長度分布（應全為 114）、
封包型別、通道分布（不應出現次通道）、first_word_invalid 比例。

### ~~韌體未過濾來源 MAC~~（C5 版已修正）

前一版任何裝置的封包都會觸發 CSI。C5 版回呼只收路由器 BSSID 的封包。

### 其他

- 進階分析與 AI 建模（CWT、EMD/VMD、CNN/LSTM 分類、Transfer Learning）尚未開始
- 無自動化測試
- 輸出為 ASCII 十進位，每個 int8 用 2~5 字元傳送（約 3~4 倍膨脹）；
  改二進位預估可將 fps 推至 120~160

## 13. 實驗配置

> 本節為前一版（ESP32 + N300、2.4 GHz）的配置。幾何推算用的是 2.4 GHz 波長，
> C5 若用 5 GHz，Fresnel 區會變窄，需用 λ ≈ 5.7 cm 重算。

以下為 2026-09-08、09-10 兩批資料的實際佈置（2026-09-16 由實驗者補齊）。
**三批資料都在同一個測試場地錄製。**

### 設備擺放

| 項目 | 值 |
|------|-----|
| 路由器離地高度 | 76 cm |
| ESP32 離地高度 | 76 cm（與路由器同高） |
| 兩端間距 | 223 cm |
| 通道 / 頻寬 | Channel 6 / 20 MHz（中心頻率 2437 MHz） |

### 位置標籤的定義

**`P0` / `P05` / `P10` / `P15` 是「在水平面上向外偏離連線的距離」，不是與設備的距離。**

路由器與 ESP32 同高（皆 76 cm），兩者的連線是一條水平線。
人坐在**連線的中點**，在**同一個水平面上**、與連線成直角向外偏移（不是上下方向）：

| 標籤 | 水平偏移 |
|------|---------|
| `P0` | 0 cm（正好坐在連線上，身體遮斷 LoS） |
| `P05` | 50 cm |
| `P10` | 100 cm |
| `P15` | 150 cm |

⚠️ **這一點很容易誤讀。** 這些標籤不構成「距離由近到遠」的序列，
所以 `P15` 比 `P10` 強**不是**反常現象——見下方「幾何推算」。

### 受測者狀態

| 項目 | 值 |
|------|-----|
| 姿勢 | 坐、靠著椅背 |
| 朝向 | 面向 ESP32 那一側 |
| 衣物 | 一般 |
| 房內其他人 | 無人、無走動 |
| 呼吸引導 | 線上節拍器 25 BPM，**兩拍完成一次呼吸** → 12.5 次/分 |
| 節拍器工具 | <https://metronome-online.com/zh/25-bpm> |

### 幾何推算（由上述配置導出）

Channel 6 的波長 λ = **12.31 cm**，半波長 λ/2 = 6.155 cm。
中點處的第一 Fresnel 區半徑 = √(λ·D/4) = **26.2 cm**。

由於 P05/P10/P15 的偏移量遠大於 26.2 cm，受測者其實坐在**高階 Fresnel 區**中：

| 標籤 | 偏移 | 路徑差 Δ | Fresnel 區數 n | 每 mm 胸腔位移的路徑變化 | 極大→盲點需移動 |
|------|------|---------|---------------|----------------------|---------------|
| `P0` | 0 cm | 0.0 cm | 0.00 | 0.000 mm | — |
| `P05` | 50 cm | 21.4 cm | 3.48 | 0.335 mm | 3.76 cm |
| `P10` | 100 cm | 76.5 cm | 12.44 | 0.892 mm | 2.30 cm |
| `P15` | 150 cm | 150.8 cm | 24.50 | 1.288 mm | **1.92 cm** |

（Δ = 2·√((D/2)² + r²) − D；n = Δ ÷ (λ/2)；胸腔沿「指向 ESP32」方向位移 s 時
路徑變化率 = 2r²/L²，L = √((D/2)² + r²)。）

**兩件事可以從這裡讀出來：**

1. **偏移越遠，對胸腔起伏越靈敏**（0.335 → 0.892 → 1.288 mm/mm）。
   這解釋了為什麼 `P15` 的突出度（13.1）和呼吸率準確度（MAE 0.19）都是四個位置中最好的
   ——它不是「離得最遠所以最弱」，反而是靈敏度最高的位置。
   `P0` 是另一套機制（身體直接遮斷 LoS），不適用這個模型。

2. **坐姿位置需要公分級的重現度。** 在 `P15`，人只要偏 **1.92 cm**，
   就會從靈敏度極大跑到盲點。目前的地面標記幾乎不可能有這種精度
   ——這是 09/08 與 09/10 訊號差 3.5 倍的**頭號嫌疑**。

> ⚠️ 上述模型只是一階近似，且與實測只有部分吻合：它正確預測了 `P15` 最強，
> 但沒有解釋 `P0` 為何也很強（不同機制），也沒有解釋 `P05`（11.2）為何略高於 `P10`（10.3）。
> 人體不是點反射體，軀幹寬度約 30 cm、已跨越多個 Fresnel 區，會有平均效應。
> **這是一個值得驗證的假說，不是已確立的結論**——驗證方法見 [TODO.md](TODO.md) 的細部位置掃描。

### `HOLD`（閉氣）組的錄製協定

位置固定在 `P10`，姿勢與 `GEO` 相同。單檔約 90 秒，分三段：

| 時間 | 動作 |
|------|------|
| 0 ~ 30 s | 以 25 BPM 節拍器正常呼吸（與 `GEO` 完全相同） |
| ≈ 30 s | **舉手一次**（作為分段標記） |
| 30 ~ 60 s | 憋氣 |
| ≈ 60 s | **舉手一次** |
| 60 ~ 90 s | 恢復呼吸 |

⚠️ **所以 `HOLD` 檔不是「沒有呼吸」的樣本，只有中間 30 秒是。**
舉手是刻意加入的動作標記，也是 CSI 上的暫態；分析時前後各避開 3 秒。

分析工具：[`segment_analyze.py`](segment_analyze.py)。

### 仍然待補

- 每次錄製的實際坐姿位置量測值（目前只有名目標籤，沒有當次量到的數字）
- 舉手的暫態在 CSI 上不夠顯著（z 只有 2~4），目前靠協定的名目時間分段而非自動偵測。
  若要自動化，需要更明顯的標記動作，或在錄製端寫入事件時間戳。
